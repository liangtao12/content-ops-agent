## 1. 测试对象与范围

| 项 | 内容 |
|---|---|
| 被测系统 | ContentOps Agent（LangGraph 六节点编排 + FastAPI + SQLite checkpoint） |
| 测试周期 | 2026.09 - 2026.11 |
| 测试环境 | 本地 Mock LLM（无 Key 离线可跑）、SQLite 持久化、Python 3.11+ |
| 测试角色 | 功能测试（用例设计 + 执行 + 缺陷跟踪），非开发 |

**在范围内**：认证与账号初始化、角色权限分离、任务创建与平台白名单、人工审批与编辑复审、合规拦截与放行理由、审批令牌绑定、排期幂等与并发、SSE 流式接口、进程重启后的 checkpoint 恢复、排期时间格式与时效校验、测试文档与实际一致性。

**不在范围内**（避免把别人的问题算成自己的结论）：

- LLM 生成内容的质量 → 由 `backend/eval/`（golden 集 + 规则护栏 44 条）负责；
- 前端视觉与响应式细节 → 只做一次界面筛选用例（CO-13），且未执行；
- 性能与压测 → 仅做了 8 线程幂等验证（CO-11），不等于并发压测。

## 2. 测试策略

1. **读源码定边界**：先读 `graph.py` / `auth.py` / `approvals.py` / `tools.py` / `persistence.py`，画出状态流转（`awaiting_human → completed / rejected`）和三条不可绕过的约束：权限分离、编辑后强制复审、令牌与内容绑定。用例优先围绕"能被绕过的约束"设计，而不是围绕页面能点哪些按钮。
2. **按风险排优先级**：P0 只给主流程和可直接造成越权/脏数据的路径（9 条），P1 给异常输入与边界（5 条），P2 给界面查询（1 条）。
3. **执行分层**：已有 pytest 覆盖的用例直接跑自动化回归并回填测试函数路径；既有用例覆盖不到的边界（时间校验）单独构造入参手工补充执行；界面类用例标注"设计待执行"，不伪造结果。
4. **失败必定位**：两条失败用例都追到具体代码位置与异常类型，并转成带复现步骤的缺陷，而不是只写"测试不通过"。

## 4. 结论

**可以放行的部分**：主流程（创建 → 审批 → 排期）、四类角色权限分离、合规失败必须填放行理由、审批令牌与内容/平台绑定、幂等键重复提交只生成一条日程、SSE 事件顺序 —— 共 12 条用例通过，且都有自动化断言兜底，可作为回归基线。

**不能放行的部分**：

1. **CO-DEP-001（P0）**：进程重启后无法恢复人工审批，`JsonPlusSerializer` 缺 `dumps` 方法。这条直接打掉项目最核心的卖点（Human-in-the-loop 跨重启续跑），属于"功能看起来有、实际不可用"，优先级最高。
2. **CO-FUNC-001（P1）**：`write_schedule` 不校验 `publish_at`，`not-a-date` 和 `2020-01-01T00:00` 都能排期成功，会产出无效日程和脏数据。建议补 ISO 解析 + 时区规范 + 未来时间校验。
3. **CO-DOC-001（P3）**：README 声称 65 个测试，实际收集 64 个。测试人数这种可核对的信息写错，会让评审对整个 README 的可信度打折。

## 5. 已知边界（不粉饰）

- 12 条"通过"是在 **Mock LLM** 下取得的，证明的是编排、中断、复审、恢复链路正确，**不代表真实模型的内容质量**；
- CO-13（按状态与关键词筛选任务）只做了用例设计，**未执行，不计入通过率**；
- 未做性能测试；CO-11 的 8 线程只验证幂等语义，不是吞吐/稳定性结论；
- 缺陷均未修复，因此本文档记录的是**修复前基线**；修复后需重跑 CO-14、CO-15 与全量 pytest 再更新本页。

## 6. 复现方式

```bash
cd backend
pip install -r requirements.txt
pytest --basetemp=../.pytest-tmp        # 61 条已执行用例
pytest --collect-only -q | tail -1      # 核对收集数量（当前 64）
```

单条用例的测试函数路径见 [test-cases.md](test-cases.md) 的"证据来源"列。
