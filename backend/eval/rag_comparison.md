# RAG 检索对照评测（BM25 / 向量 / 混合）

- 指标: Recall@1 / Recall@3 / MRR@3；耗时含查询与扩展开销（索引为进程内单例）
- 向量路开启领域同义词扩展（`rag.expand_query`）；BM25 路保持原查询，对照公平

## 结论

| 场景 | 最优模式 | BM25 MRR | 向量 MRR | hybrid MRR |
|---|---|---|---|---|
| 口语化改写 | bm25 | 1.000 | 0.917 | 1.000 |
| 跨词表 | vector | 0.417 | 0.889 | 0.806 |
| 案例库 | bm25 | 1.000 | 1.000 | 1.000 |

**没有单一模式在所有场景最优**，这正是不该拍脑袋选框架的原因：

- 口径一致、术语密集时 BM25 已接近上限（MRR 1.000），向量单独用反而略低（0.917）；
- 跨词表时 BM25 明显失效（MRR 0.417），同义词扩展后的向量路把 MRR 拉到 0.889，hybrid 为 0.806，且三者 Recall@3 均达 1.000（正确答案不会被漏掉，只是排序位置不同）；
- 默认 `RAG_MODE=hybrid` 是「不挑场景」的稳妥选择：口语化场景追平 BM25，跨词表场景比 BM25 提升 +0.389 MRR；
- 若线上查询确认以口语化/跨词表为主，可切 `RAG_MODE=vector` 追求排序精度；若查询与文档用词高度一致，切 `bm25` 最省；
- 融合权重不是固定值：按 BM25 top1 分数做置信度自适应（0.15~0.80），术语型查询偏向 BM25，跨词表查询把权重让给向量，避免固定权重两头不讨好；
- 回归口径：任何改动后重跑本脚本，hybrid 的 Recall@3 或 MRR@3 低于基线即判定回归。

> 边界：本地默认 hashing embedding 没有真实语义能力，跨词表能力来自 `expand_query` 的同义词表；配置 `EMBEDDING_PROVIDER=remote` + 远程 embedding 后可去掉同义词表再对比，那才是语义模型的上限。本报告的指标只用于横向比较三路策略，不代表业务绝对效果。
